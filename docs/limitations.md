# 做不到什么

**这一份比「能干什么」更值得读。**
**因为「以为它管」比「它不管」更危险** —— 你会因为以为它在看着，而放过某个本该检查的地方。

---

## 一、它拦不住「绕过」

**它挂在 `write` / `edit` 这两个工具上。**
用**别的方式落盘**（跑脚本、`Out-File`、`>>`、别的工具）—— **它就看不见。**

**⚠️ 而"看不见"和"没发生"是两件事**：
- **它看不见** = 它不知道有这回事
- **"没发生"** = 你确认过没有这回事

**→ 所以这个项目里另有一个「审计」的活**：
**定期扫一遍"窗内被改动的文件"，看哪些改动没经过那两个工具。**
**⭐ 而那是审计，不是沙箱** —— **它只能事后告诉你"发生过"，拦不住任何东西。**

**⚠️ 而它自己有一条边界要说清**：**"归因不到"和"没改动"也长得不一样。**
（一个文件被改了、但找不到是哪次调用改的 —— 那要**单独报**，不能混进"没事"里。）

---

## 二、它拦不住「语义错」

**它能问「这个 `.py` 解析得了吗」**（解析器说了算），
**问不了「这段逻辑对不对」。**

```python
try:
    do_something()
except Exception:
    pass          # ← 语法完全正确。而它可能吞掉一个真错误。
```

**→ 那类只能靠**：
- **lint**（例如"未定义的名字"—— `ast.parse` 抓不到，`pyflakes` 能抓）
- **读代码**
- **你的脑子**

**⚠️ 而"能不能解析"这条判据本身也不完备**：
**它能抓"写坏了"，抓不了"写对了但写错了"。**

---

## 三、它不是零误报

**非平凡性质不可能无误报**（Rice 定理）——
**任何"看着像那么回事"的静态检查，都会在某些正确代码上报警。**

**→ 所以设计上给了两条出路**：
1. **熔断**：连续被拒 N 次 → 自动放行（**绝不用"无限拦"惩罚"诚实报告卡住"的人**）
2. **申辩出口**：被拒的回执里直接写着"认为这是误报 → 怎么申辩"

**⚠️ 而熔断本身有一个要分清的地方**：
> **「取消了放行」和「计数器坏了」看起来一样。**
**→ 所以每次拒绝都要带一个"还在动的量"**（"这是第 N 次被拒"）——
**否则你分不清"这是设计"还是"这坏了"。**
（同族的两个例子：「没变化」vs「还没发生」；「没查」vs「没问题」。**都要一个还在动的量来分开。**）

**⚠️ 而熔断只该给"判据可能不成立"的规则**：
判据来自**权威工具**的（解析器、字节检查）—— **它不可能不成立** →
**对它们熔断只有副作用**（让一个确实写坏了的东西落盘）。

---

## 四、它只在「你动手那一刻」生效

**它拦不了一个已经写下去的错。**
**发现晚了就是晚了。**

**→ 所以它不是"质量保证"，是"最后一道门"。**
**而最后一道门的意思是**：**门里面的东西，它一概不管。**

---

## 五、它改不了「看到之后动不动」

**它能把提醒送到你眼前** —— **而任何文案都改不了"看到了不动"。**

**⚠️ 而这条要说清**：**那不是"信号不够硬"** —— 是**"愿不愿意"**。
**如果你把提醒改成催促，它就开始变成墙纸**（墙纸的意思是：**你开始不看它**）。

**→ 所以这里有一个设计上的自我限制**：
**提醒说到"该做什么"就停，不升到"请现在处理"。**

---

## 六、它不替你判断

**「这条算不算一个坑」「这该归到哪一组」「这条判据值不值得写成规则」** ——
**它只把原材料摆好，拍板永远是人。**

**⚠️ 而"别自动归"不是保守，是有理由的**：
**自动归类会把"算不算新坑"这个判断埋掉** ——
**而那个判断埋掉之后，清单就开始积累"其实不是坑"的东西。**
**→ 然后没人再认真看那份清单。**

**同一件事的另一面**：**"看了、判定不进清单"也要留痕** ——
**否则它和"漏了"长得一样。**

---

## 七、它有些地方**天生不完整**（而我们知道）

| 不完整的地方 | 为什么 |
|---|---|
| **只能看"命令串"** | 规则引擎看不见别的工具的**参数**（例如"某个工具传了一个 PDF 地址"那种，它看不见） |
| **有些"归因不到"** | 改动发生了但找不到来源 —— 那要**单独报**，不能算进"没事" |
| **"次数"是下限** | 自己看出来、直接改掉、没跑过的东西**没有痕迹**，数不进来 |
| **"谁发现的"填不填靠人** | 那是语义，**机器填不了**。没填 = 那个数只能算"已知那部分" |

---

## 八、最后一条：**它救不了"没记下来"的坑**

**整套东西的前提是"你踩了会记"。**
**→ 而"记"这个动作，如果只靠"记得"，它就会漏。**

**所以这个项目里连"记"这件事都做了两条路**：
- 一个**工具**（会话里调）
- 一个**纯脚本**（不依赖工具表，任何环境都能跑）

**⭐ 因为**：**"给了一个工具"不等于"打通了"** ——
**判据仍然是那句：它自己会发生，或者它自己会提醒。**

---

## 九、「工具失败」有**三层**，而它们**不是都看得见**

**这是被真实验收逼出来的一张表** —— 有人触发了一次失败，而护栏没响；
顺着查才发现：**"失败"不是一个东西，是三个，而它们的可见性完全不同。**

| 种 | 例子 | 护栏看得见吗 | 靠什么覆盖 |
|---|---|---|---|
| **① 工具执行后报错** | 文件操作失败（`FsError` 那类） | ✅ **看得见**（`tool/result` 顶层有 `error` 字段） | **"失败就提示记一笔"那条** |
| **② 命令返回非零** | `exit code 1` | ❌ **看不见** —— **退出码在输出文本里，不是结构字段** | **定期重扫**（从会话日志里捞） |
| **③ 工具被护栏自己拒掉** | 一条被拦下的写入 | ✅ **看得见** —— **被拒本身也是一次结果**（**见下面的更正**） | **拒绝回执本身 + 台账的 `refused`** |

**⚠️ 而三层里，有一个"钩子"只覆盖一层** —— 而**如果不说清，人就会以为它覆盖三层**。

> **「以为它管」比「它不管」更危险。**

**⭐ 而这张表的由来本身就是这条判据的示范**：
**"它没响"和"它不该响"在现象上一样** —— **所以每一层都要能回答"我覆盖不覆盖它"。**

**⚠️ 而 ② 那一层还有个更麻烦的地方**：**它恰恰是量最大的一类**
（在某个真实项目里，几千条失败信号绝大多数是它）—— **而它只能靠"事后捞"。**

### ⚠️⚠️ 更正：上表第 ③ 格**写错过**（留痕，因为这份文档是给人看的）

**上一版写的是**：「**③ 工具被护栏拒 → ❌ 看不见（它没执行）**」——
**→ 那是错的。** 而推翻它的不是推理，是**真实运行**：

> **在一次护栏拦下写入之后，"失败就提示记一笔"那条**响了** ——
> 而它显示的错误码是「**（没有 code）**」。

**→ 真实的形状是**：**那条结果里的 `error` 有两种**：
| 哪一种 | 有没有 `code` |
|---|---|
| **宿主的前置校验拒** | **有**（`FS_NOT_OBSERVED` / `FS_EDIT_NOT_FOUND` / `FS_STALE_VERSION`） |
| **被护栏自己拒** | **没有**（`error` 里没这个字段） |

**⚠️ 而"看不见"那个结论，来自一句推理**：**"它没执行，所以不会有结果"** ——
**而那句推理漏了一件事**：**"被拒"本身也是一次结果，宿主会把它记成一条记录。**

**★★ 而这次更正本身就是下面第五层的示范**：**推理说得通的，未必是跑得通的。**

## 十、验收有**五层**，而它们一层比一层严

| 层 | 手段 | **它证什么** | **它证不了什么** |
|---|---|---|---|
| **1** | **语法检查 / 编译器** | **能不能解析** | **名字存不存在、变量初始化了没有、逻辑对不对** |
| **2** | **单元测试 / 挂具** | **代码路径通不通** | **那条路径会不会被**走到**** |
| **3** | **喂合成输入** | **那个函数还活着吗** | **它有没有被**调用**** |
| **4** | ⭐ **跑到真实路径** | **那条路径有没有被走到** | **它响的时候，别的开关是开着的吗** |
| **5** | ⭐⭐ **跑到真实路径 + 检查开关状态** | **它在"用户当前配置下"会不会被看见** | — |

**⚠️ 每一层都有"我就到此为止了"的时刻，而那就是它出事的地方**：
- **只做第 1 层** → **"语法绿 = 完成"**（而截断 / 未定义名字 / 变量未初始化**都能通过语法检查**）
- **只做第 2 层** → **"挂具绿 = 完成"**（而**一个从没被走到的功能，挂具是绿的**）
- **只做第 3 层** → **"函数还活着 = 完成"**（而**一个被配置关掉的功能，函数是活的**）
- **只做第 4 层** → **"它响了 = 完成"**（而它可能只在**你测试的那个配置组合**里响）

**⭐⭐ 而第 5 层是最后才被发现的**：
> **它响了 —— 而它响的时候，别的开关是开着的吗。**

**具体事故**：**两条"故障类"的提醒，被挂在一个"偏好类"的总开关下面** ——
**→ 用户为了清静关掉欠账提醒，同时把"配置断了"和"判据不响了"也一起关掉了。**
**→ 而关掉之后，输出里"什么都没有"** —— **"用户选择不看"和"这里坏了"，长得一模一样。**

**★★★ 所以有一条统一的判据**：
> **任何"关掉之后什么都看不见"的开关，都要问一句：**
> **「它关掉的里面，有没有"故障"这一类？」**
> **偏好可以关；故障不该被偏好关掉。**

**而这一条的形态，和这个项目反复遇到的那些是同一个**：
**两个不同的东西长得一样，而没有任何信息能区分它们。**
（"跳过"和"没问题"、「还没跑过」和「0 条候选」、"存量"和"事件没发生" ——
**现在是"用户不看"和"这里坏了"。**）


---

## 十一、**每一道闸都有它够不着的地方 —— 而够不着什么，取决于它挂在哪一层**

**这是这一整套东西里最一般的一条限制**（而它比"某条规则不准"更要紧）。

| 闸 | **挂在哪一层** | **它够不着什么** |
|---|---|---|
| **解析闸**（写下去的能不能解析） | **工具**（`edit` / `write`） | ⚠️ **用脚本/命令行写的文件** |
| **定期重扫** | **时间**（比如 24 小时一次） | ⚠️ **"刚发生的"** |
| **"失败就提示记一笔"** | **工具结果的结构** | ⚠️ **命令返回非零**（在文本里）｜**被拒的**（不产生结果） |
| **启动自检** | **进程启动那一刻** | ⚠️ **"这次启动之后坏掉的东西"** |

**⭐ 而它有一个真实的代价，不是一个抽象的说法**：
> **这个项目在一次整树对账里报出「18 处绕过（`write`/`edit` 之外的落盘）」** ——
> **那 18 处不是"审计发现的问题"，是"解析闸够不着的地方"。**

**★★ 所以加一道闸的时候，要问三个问题**（**第 ② 个才是重点，而它最容易跳过**）：
```
① 它挂在哪一层？（工具 / 产物 / 时间 / 结构 / 启动）
② 那一层够不着什么？
③ 够不着的那些，有没有别的路覆盖？（没有 → 那是个要写在这里的缺口）
```

**⚠️ 而不要指望"把闸挂得更高"能解决它** ——
**挂得越高，够不着的东西越抽象**（**而抽象的东西，人看不见**）。

**⚠️ 而它推出一句更难听的话**：
> **这套东西的上限，不是「能拦多少」，是「它拦不住的那些，人**还愿不愿意看**」。**
> **（"抽象的东西只能靠人看" —— 而人看不看，不是这套东西能决定的。** 那个 18，就是它的量级。）

**⚠️ 而它推出一句更难听的话**：
> **这套东西的上限，不是「能拦多少」，是「它拦不住的那些，人**还愿不愿意看**」。**
> **（"抽象的东西只能靠人看" —— 而人看不看，不是这套东西能决定的。** 那个 18，就是它的量级。）

## 十二、附：**一个"取一段"的动作，该有它的守卫**

**这一条很小，而它来自一次真实的代价**（**同一个错，一个晚上犯了 9 次**）。

**那次的具体错误**：
```python
indent = src[line_start:i]     # ✗ 这不是"缩进"，是"行首到某个子串之间的一切"
                               #   而那一行是 `		const child = spawn(` →
                               #   取到的是 "		const child = " —— 被当成缩进用了
```
**⭐ 而正确写法与它的差别是可写出来的**：
```python
indent = re.match(r"[\t ]*", line).group(0)   # ✓ 它只可能给出空白
```
**→ 两者只在「那一行以空白开头、且子串刚好是第一个 token」时才相等。**

**⚠️ 而零成本的兜底是一行断言**：
```python
assert indent.strip() == "" and set(indent) <= {"\t", " "}, f"不是缩进：{indent!r}"
```
**★★ 那一行断言的成本是零；而它省下的，是"三次修 + 三次把损坏加深"。**

**⭐ 一般形式**：**"取一段"的时候，先问「我怎么知道取到的正是我要的那一类东西」** ——
**答不出来 → 换成"按形状取"（正则 / 解析），而不是"按位置取"。**


### 附：**那两个"后台活"的 stderr 落在哪** —— 以及**为什么现在没有人读它**

**机制**（2026-09-27 加）：那两个后台脚本（定期重扫 / 两条捞回）的 **stderr 现在会落盘**：
```
<脚本路径>.stderr.log        （stdout 仍然丢弃 —— 那是**有意**的：不让子进程拖住宿主）
```
**⭐ 而"落盘"和"有人看"是两件事** —— 现在**只有前者**。

**⚠️ 而"要不要接进注入"这件事，我判定**现在不做**** —— 理由是**一个数**：
> **那些文件现在还不存在**（**新版还没重启过**）→ **所以"它会不会非空"现在数不出来**。
> **而在"那件事会不会真的发生"还不知道的时候，去做"看得见"那一半 —— 那是在猜。**

**⭐ 回程票**（**别让它变成"忘了"**）：
```
· 什么时候回来看：**那两个后台活跑过几次之后**（`spawned` 在凭据里，可以数）
· 看什么数：      **`*.stderr.log` 出现过内容吗**
· 判据：
    · **没出现过** → 判「不用做」，并**留痕**（评估过、没做、为什么）
    · **出现过**   → **那才接进注入**（让它出现在会话眼前）
```

**⚠️ 而在那之前，如果你想知道"那两个脚本有没有报错"** —— **去看那个文件就行**：
```
<你的脚本目录>\*.stderr.log
```
**⭐ 所以这一条不是"缺了个功能"，是"缺了个人去看它"** —— **而"说清它存在"就是这一条的交付。**
