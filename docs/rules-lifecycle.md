# 一条规则的一生

> ⚠️ **来源说明（先说清，免得你把下面的数当权威）**：
> 这份文档里**描述"形状"的部分**是通用的（那种生命周期几乎所有静态检查工具都有）。
> 而**具体的数字**（比如"响过 5 次才值得调查"）来自一份**外部调研**，
> **那份调研记录不在这个仓库里** —— 所以我把它们标成「**暂定**」，
> **你应该按自己的量级重新定，并且把"为什么是这个数"写下来。**
>
> **⭐ 而本文档自己就是那条纪律的示范**：**每个数都带"它的依据是什么"。**

---

## 零、为什么要有"一生"这个概念

**因为一条规则会老。**

它出生时是为了拦住一个真坑；半年后那个坑可能已经不可能再犯（环境变了、那个工具不用了），
**而它还在那里拦人** —— **那时它的成本大于收益，而没有任何东西会告诉你。**

**→ 所以每条规则都要能回答四个问题**：

| 问题 | 为什么 |
|---|---|
| **它拦过几次？** | **从来没响过的规则 = 只有成本** |
| **它拦错了几次？**（被申辩过几次） | 一条老是拦错的规则，会让人**开始无视它** |
| **它的依据是什么？** | **一个没有依据的阈值，和一个没有依据的规则一样，都是"只有成本"** |
| **什么时候该回来看它？** | **否则它会一直挂着**（而"一直挂着"和"经过判断后保留"长得不一样） |

---

## 一、出生的两种方式（**多数的规则不该是"设计"出来的**）

| 方式 | 说明 | 风险 |
|---|---|---|
| **从真实事故里长出来** ✅ | 你踩了 → 记下来 → 发现"这个形状会反复出现" → 写成规则 | 判据可能写不准（**那是可以慢慢修的**） |
| **凭想象设计** ❌ | "这个应该会出问题吧" → 直接写规则 | **它会拦你**，而**你没有任何证据说它该拦** |

**⭐ 判据**：**这条规则背后有一次真实的、能贴出来的事故吗？**
**没有 → 先别写。** 那样你至少不会造出一条"从来不响"的东西。

---

## 二、分级：**从"记着"到"拦住"有一条梯子**

**不是所有坑都值得写成规则** —— 有些只能"提醒"，有些连提醒都不该发。
这个项目里那条梯子长这样：

```
① 只记着（进清单，不进提醒）
   理由：它很少见 / 或者它的判据写不出来
        ↓
② 提醒（warn）—— 说话，但不阻止
   理由：它可能出问题，而"可能"不该拦住人
        ↓
③ 拦住（block）—— 阻止，并说清为什么
   理由：**它必然出问题**，而"必然"才值得拦
```

**⚠️ 而阶数越高，越要克制**：
**这个项目的实现里，`block` 类的规则只有很少几条** ——
**因为一条规则一旦开始频繁拦人，人就会绕着它干活**，那时**它的成本大于收益**。

---

## 三、每个阶段该问的问题（**"什么时候该做什么"**）

**下面那条梯子的数字是「响过几次」**（拦 + 提示，**不是只算拦**）——
因为"这条规则响得对不对"才是争议率的分子。

| 响过几次 | 该做什么 | 为什么 |
|---|---|---|
| **1–2 次** | **什么都别做** | 偶发。**样本太小**，任何结论都是噪音 |
| **3–10 次** | **该开始调查** | 够多了：能看出"它是不是在同一个形状上反复响" |
| **11 次以上** | **精化或退役** | **要么把判据收窄**（让它只拦真正该拦的），**要么判定它不值得留** |

**⚠️ 而这三级是「暂定」的** —— 来源是一份外部调研，**数字本身没有魔力**。
**重要的是那个形状**：**别在 1–2 次时就动手，也别在 11 次之后还不动。**

---

## 四、误报：**"能不能测"比"测出来多少"重要**

**每个静态检查都会误报**（非平凡性质不可能无误报）。
**所以真正的问题不是"能不能做到零误报"，而是"它的误报率能不能被量出来"。**

**⭐ 判据**：
> **能被真实语料校准的网（哪怕会误报），胜过校准不了的网（哪怕很少出错）。**
> 那不是"谁更可靠"的差别，是"**错了会不会被发现**"的差别。

**→ 所以**：
- **有「同类但正确的样本」的规则**（例如"这个 `.py` 解析不了" —— 正确的样本就是"能解析的 `.py"）→ **才谈得上"误报预算"**
- **没有的** → **如实标「测不了」**，**别报一个算不出来的百分比**

**⚠️ 而"检查什么时候重测"这条口径，我们改过**：
外面常见的做法是"**滚动 30 天**"——
**而时间本身不改变任何东西**。**该复看的信号是"规则变了"。**
→ **所以改成「每次规则变更时重测」。**

---

## 五、退役：**退役必须有实际动作**

**"在提示里说一句『这条该退役了』"—— 那不是退役，那是一条新的提醒。**

**真的退役 = 三件事**：
1. **从生效的规则表里摘掉**（它不再拦任何东西）
2. **在数据里标 `retired` + 为什么 + 什么时候**（**留痕，不是删除**）
3. **如果它的坑还在**（只是不值得做成规则了）→ **把它退回"只记着"那一级**，别让它消失

**⚠️ 而"退役"最难的一步是承认**：
**你当初写它的时候是对的，而现在它不值得留了。**
**那两件事可以同时成立** —— **而如果没有一条"回来看"的机制，你就不会去重新判断。**

---

## 六、复核：**别用"过期"，用"回来看的条件"**

外面常见的做法是给每个例外/判定设一个**过期时间**。
**而这个项目的经验是：在我们的量级上，"时间到了"什么都不会变。**

**→ 改成「回看条件」**，而且**它必须可判**：

```
❌ 三个月后回来看            ← 三个月后，什么都没变
✅ 等「这件事有了能校准的语料」 ← 那个条件一满足，就真的该回来看
```

**⭐ 而"回看条件"要分两类**（**而"只能人看的"那类，不该发提醒**）：

| 类 | 例子 | 该不该发提醒 |
|---|---|---|
| **机器能判** | "等误报语料里出现对应形状的样本" | ✅ **发** —— 条件满足时提一句 |
| **只能人看** | "等这类错误有了写入前可判的形态" | ❌ **不发** —— **发了也没人能照做，那是墙纸** |

**⚠️ 而那第二类是这条纪律里最容易搞错的地方**：
**"我想到了一个问题"不等于"我该发一条提醒"。**

---

## 七、把"它什么时候响"记成数据

**上面每一条都需要数据支撑** —— 所以**规则表不该只是"规则"**，还该带：

```jsonc
{
  "id": "…",
  "why": "它为什么算坑（**这是它存在的理由**）",
  "can_precheck": "可 | 部分 | 不可",   // 判据能不能机械写出来
  "revisit_kind": "evidence | human",   // 回看条件能不能机器判
  "revisit_when": "…",                  // 那个条件是什么
  "promoted_to": "…",                   // **如果它已经被写成规则** —— 升成了哪条
  "retired": false                      // **如果它退役了** —— 为什么、什么时候
}
```

**⭐ 而最后两个字段有个共同的教训**：
**「能不能写成规则」和「写没写」是两件事** ——
**而"写没写"只能在"写的那一刻"记下来，不能事后从别处反推。**
（我们试过反推：结果把"**本来一开始就是规则**"的那些，也算成了"**升格来的**"。）
