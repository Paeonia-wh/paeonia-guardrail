# paeonia-guardrail

> **这是一个 [DSH（DeepSeek Harness）](https://github.com/deepseek-ai) 插件。如果你不用 DSH，这份代码跑不起来。**
>
> **但「踩 → 记 → 归类 → 升格 → 拦」这五步的方法，你可以照着在自己的工具里实现。**
> —— 见 [`docs/porting.md`](docs/porting.md)（**用 Claude Code / Codex 的话，这五步怎么落地**）。

---

## ⚠️ 先说做不到什么（这一节比「能干什么」重要，所以放前面）

| 做不到 | 为什么 |
|---|---|
| **拦不住"绕过"** | 它挂在 `write`/`edit` 这两个工具上。**用别的方式落盘（脚本、`Out-File`、别的工具）它就看不见** —— 那是**审计**，不是沙箱 |
| **拦不住"语义错"** | 它能问「**这个 `.py` 解析得了吗**」（解析器说了算）；**问不了「这段逻辑对不对」**。`except: pass` 语法完全正确，而它可能吞掉一个真错误 |
| **不是零误报** | **非平凡性质不可能无误报**（Rice 定理）。所以设计上给了**熔断**（连续被拒 N 次自动放行）+ **申辩出口** |
| **只在你动手那一刻生效** | 它**拦不了一个已经写下去的错** —— 只能在你写的那一刻拦。**发现晚了就是晚了** |
| **改不了"看到之后动不动"** | 它能把提醒送到你眼前，**但任何文案都改不了「看到了不动」**。那是"愿不愿意"，不是"信号够不够硬" |
| **它不知道「该怎么跑你的文件」** | 它知道**你写了一个文件**；它不知道**那个文件的入口在哪、依赖是什么、跑起来要多久**。所以「未定义变量 / TDZ」这类**要跑一次才知道**的错，它拦不住 —— **那落成项目纪律（写完跑一次挂具），不是插件规则** |
| **它不替你判断** | 「这条算不算一个坑」「这该归到哪一组」——**它只把原材料摆好**，拍板永远是人 |

**⚠️ 而最要紧的一条**：
> **它拦的是「必然出问题」的事，不是「可能出问题」的事。**
> 一条规则一旦开始频繁拦人，人就会绕着它干活 —— **那时它的成本大于收益。**
> 所以这个项目里 `block` 类的规则**只有很少几条**，而**每一批提醒都必须在"归零"时静默**。

## 它是什么

一个**自检护栏**：把「我踩过的坑」变成**会在你动手前说话的规则**。

**它的五步是这样一条链**：

```
踩坑 → 记下来 → 归类 → 升格 → 下次拦住
       ↑         ↑      ↑        ↑
    （自报池）（坑清单）（规则表）（拦/提示）
```

**而这条链上每一步都有同一个要求**：

> **如果一件事要求「某人记得做」，它就不算完成。**
> **完成的标准是：它自己会发生，或者它自己会提醒。**

**→ 所以它的形态不是"一个查得到的清单"，而是"一个会在会话里自己说话的注入"。**

### 四个不变量（都是被真实代价换来的）

| 不变量 | 由来 |
|---|---|
| **改数据免重启** | 规则表和阈值表都是**数据文件**（按 mtime+size 判断，改完下次生效）。**改一条规则不用重启插件** |
| **坏数据必须 fail open 到"仍有设防"** | 数据坏了 / schema 不认 / 某条非法 → **整份回落到代码里的默认值**。**不是"全放行"，也不是"报错"** |
| **提醒必须在归零时静默** | 每条注入都带一个数；**那个数归零它就消失**。**不为零才说话** —— 否则就是墙纸 |
| **闸要挂在它真能判的那一层** | 挂在**工具**上（`edit`/`write`）／挂在**产物**上（有东西落盘）／挂在**时间**上（定时）—— **而每一层都有它够不着的地方**。⚠️ **一个真实数字**：我们说「审计发现 18 处绕过」，而真相是「**那 18 处是解析闸够不着的地方**」—— **闸挂在工具上，而有人从脚本落盘，它就看不见**。见 [`docs/limitations.md`](docs/limitations.md) 第十一节 |

## 怎么装（**你必须是 DSH 用户**）

**门槛**：它 `import` 了 DSH 自己的包（`@deepseek-ai/dsh-tools`）——
**离开 DSH 宿主，`lib/index.js` 加载不了**。这不是配置问题，是设计。

```bash
# ① 放进 DSH 能加载的插件目录（按你的 DSH 版本，路径可能不同）
git clone <this-repo> <your-dsh-plugins>/paeonia-guardrail

# ② 按 cordis.patch.example.yml 写一份你自己的配置
#    ⚠️ 里面每一项都有注释；**带 <尖括号> 的都是要你填的**
cp cordis.patch.example.yml <your-config>/paeonia-guardrail.yml

# ③ 重启 DSH，然后跑一次框架级自检
node verify/verify_framework.mjs      # 期望：17 通过 / 0 失败
```

**⚠️ 装完之后它不会立刻拦人** —— 默认只有 **2 条 `warn` 类规则**（提示，不拦）。
**那 7 条 `block` 类的规则是注释掉的**，因为：

> **一个刚装上的插件不该立刻开始拒绝人。**
> **而它默认那几条，全是「Windows + PowerShell 5.1 + 中文环境」下的实测坑 —— 你的环境里多半不成立。**

## 怎么用

**你不用"用它"** —— 它挂在那里，**在你动手前说话**：

```
· [护栏 G11 / 坑清单 P01] 这条命令合并了 stderr 和 stdout…
  ← 台账记录：这条规则拦过 3 次｜提示过 17 次
→ 改法：<怎么做才对>
  （第 1/5 次被拒。再被拒 4 次本关会自动放行并记为熔断。）
```

**而每次会话启动，它会注入一段"还没做完的事"**（归零就静默）：

```
· 待归类 N 条（已按形状归好类，每条带最接近的已有坑）：
    3. 【引号层级】…
       → 最接近：P32「字符串里嵌同种引号」
    → 该动作：把上面每条归到一组，或判定「不进清单」
  ⏱ 这份展开是 2 分钟前算的（取自产物本身）
```

**而它给的每一样东西都能查**：

```bash
node -e "…"    # 或者用插件注册的那几个只读工具：
               #   guardrail_rules_status   —— 现在生效哪几条、来源是数据还是代码默认
               #   guardrail_thresholds     —— 全部阈值 + **哪些是"拍的"（欠依据）**
               #   guardrail_rule_profile   —— 每条规则拦过/提示过/被申辩过几次
               #   guardrail_lookup         —— 按关键词查坑清单
```

## ⭐⭐ 怎么挖你自己的坑（**核心 —— 它不给答案，给工具**）

**这份代码的作者踩的坑，你一个都不必踩。** 你要做的是**把你自己的坑**变成规则。

**而那件事的难点不在"写规则"，在下面这四件事** —— 这也是这个项目真正想分享的东西：

### ① 先别想着"拦"，先想着"记"

**规则是结果，不是起点。** 起点的形态是一个**只进不出的池子**：
```
每踩一次 → 往池子里写一条：它是什么 / 症状 / 证据 / 什么情况下会犯 / 是谁发现的
```
**⚠️ 而关键的一条**：**"是谁发现的"这个字段，机器填不了**（那是语义）。
但**没有它，你就答不了「哪个检查手段真的抓到了东西」** —— 而那正是你下一该改哪个检查的依据。

### ② 归类那一步，**最难的部分是机械的**

**"这条自报该归到哪一组"** 看起来要判断，其实**难的那半是机械的**：
**按形状聚类 + 找最接近的已有坑** —— 那是脚本能算的（这个项目里有 `expand_pending.py` 的做法可参考）。
**→ 把人从"读一遍池子、想一遍、再展开"缩到"点头或否"。**

**⚠️ 而有一条不能省**：**别自动归。**
**归类的产出是"原材料"，拍板永远是人** —— 因为"算不算一个新坑"**没有可靠的自动判据**。

### ③ 升格之前，先回答四个问题

```
① 判据能不能写出来？     —— 机械可判 / 要理解语义
② 写出来长什么样？       —— 给一条**具体的判据草案**
③ 会不会误报？           —— **有真实语料能测吗？有就测，没有就如实说「没测」**
④ 判据写不出来 →        —— **明确说「这条拦不住，只能提醒」**
```

**⚠️ 而第 ④ 条最容易被绕过** —— 因为**"给一条看着像那么回事的判据"太容易了**。
这个项目里真的发生过：一条规则的判据写着「命令同时含 `2>&1` 和 `git|npm|rg`」——
**而它拦的是"命令里有那些词"，和它声称要管的事毫无关系。**
**→ 一条判据看着像那么回事、但抓的不是那个东西 —— 那是它能犯的最坏的错。**

> **prior art**：**一条从不触发的规则 = 只有成本。**

### ④ 选检查手段时，先问「**它错了会被发现吗**」

**能被真实语料校准的网（哪怕会误报），胜过校准不了的网（哪怕很少出错）。**
那不是"谁更可靠"的差别，是"**错了会不会被发现**"的差别。

**→ 所以**：有「同类但正确的样本」的规则才谈得上误报预算；
**没有的，如实标「测不了」** —— 别报一个算不出来的百分比。

## 环境要求

| 层 | 要求 | 没有会怎样 |
|---|---|---|
| **① 硬门槛** | **DSH 宿主** | **`lib/index.js` 加载不了**（它 import DSH 的包） |
| **② 运行时** | **Node.js**（ESM） | 加载不了 |
| **③ 可选依赖** | **Python 3**（**只有那几个配套脚本用**） | **插件照常工作**，只是少了"展开/对账"这几个后台助手 |
| **④ 环境相关** | **Windows + PowerShell 5.1 + 中文控制台** | **插件照跑，但默认那几条规则多半不适用** —— 它们是那个环境的实测坑 |

**⚠️ 而第 ④ 层要特别说清**：这个项目的规则**不是"通用最佳实践"**，是**"某些具体环境里真实炸过的东西"**。
**你的环境不同 → 你的坑不同 → 那正是为什么它默认只开两条 `warn`。**
