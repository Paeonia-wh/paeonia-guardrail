# ⚠️ 这个目录里的 5 个挂具，**本来就跑不过** —— 那不是仓库坏了

**它们是这个项目作者的「实例级验收单」** ——
**而它们断言的是作者自己那套规则**（`Windows + PowerShell 5.1 + 中文控制台` 环境里实测出来的那些坑）。

**而这份仓库默认**不开**那些规则**（见下面的「为什么」）——
**→ 所以你跑它们，会有几个是红的。而那是对的。**

---

## 为什么默认不开那些规则

**因为一个刚装上的插件不该立刻开始拒绝人。**

**而那些规则全都是"某个具体环境里真实炸过的东西"** ——
**你的环境不同 → 你的坑不同** → **照搬它们，你会被一堆跟你无关的规则挡住。**

**→ 所以默认只开两条「提示类」规则**（`warn`：说话但不阻止），
**另外 7 条（含 3 条会**阻止**你的）作为注释留在 `lib/rules.js` 里。**

---

## 那你该跑什么

**跑它：**
```bash
node verify/verify_framework.mjs
```
**那是**框架级**的验收 —— 它不依赖作者那套规则，也不依赖 DSH 的包。**
**它验的是这个框架的四个承诺**：规则能从数据加载 / 坏数据会回落到"仍有设防" /
阈值读不到会回落 / 解析闸对坏代码会拦、对好代码放行。

**⚠️ 如果**那个**也跑不过 —— 那才是真问题**，请开 issue。

---

## 而这 5 个为什么还留在这里

**因为它们是「这个项目当初是怎么验收的」的真实记录** ——
**而那份记录本身是有价值的**（**它示范了"验收单应该长什么样"**：断言具体、带反例、能复跑）。

**⚠️ 而它们是**故意**不随默认规则走的** ——
**如果你启用了那 7 条规则，它们多半就会通过**（**因为那时它们断言的东西存在了**）。

---

**⭐ 一句话**：**`verify/verify_framework.mjs` 是这个仓库的健康检查；这 5 个是作者的病历。**
